# task-dashboard-backend — контекст для Claude Code

## Що це
Спільний бекенд для кількох незалежних панелей IkorkaShop:
`task-dashboard` (проєкти/задачі), `ikorka-sysadmin` (техніка/активи/
паролі/задачі сисадміна), `ikorka-luiza` (особиста панель власниці).
`ikorka-coo` — навмисно НЕ тут, окремий сервіс/база (`ikorka-coo-backend`).

## Стек
- Node.js + Express (`server.js`), PostgreSQL через `pg`
- Деплой: Railway, автодеплой при пуші в `main`
- Схема: `schema.sql` — виконується вручну в Railway → Postgres → Data,
  НЕ автоматично при деплої

## Авторизація
PIN у заголовку `x-pin` → роль через `resolveRole`. Ролі:
`owner`, `manager`, `sysadmin`, `evgeniya`. Хто що бачить — дивись
`requireRole(...)` на кожному роуті; `credentials` (паролі) — тільки
`owner`+`sysadmin`, навіть `evgeniya` без доступу.

## Стійкість до помилок
Усі `app.get/post/patch/delete` обгорнуті (на самому початку файлу) так,
що кинута помилка з async-хендлера йде в `next(err)` замість того, щоб
зависнути без відповіді. Останній `app.use((err,req,res,next)=>...)` в
кінці файлу ловить це й повертає нормальний JSON 500 з CORS-заголовками.
Без цього невдалий запит (напр. відсутня таблиця) висів до таймауту
Railway, який підставляв власну fallback-відповідь без CORS —
браузер бачив це як "Failed to fetch", і оскільки кілька вкладок
вантажаться через `Promise.all`, одна зламана таблиця валила весь
дашборд. **Якщо додаєш новий роут — цей захист вже працює автоматично,
нічого додатково обгортати не треба.**

## Верифікація змін БЕЗ засмічення equipment_log
Коли перевіряєш новий/змінений код прямими curl-запитами до прод-API
(а не через реальний фронт) — і викликаєш `POST/PATCH/DELETE /api/equipment*`
— додай заголовок `x-claude-verify: 1`. Це не мокає й не блокує сам
запис (мутація в БД реальна, поведінку перевіряєш чесно), але сервер
пропускає автоматичний запис у `equipment_log` (created/status_changed/
zone_changed/deleted/inventory_check), який інакше засмічує "Тижневу
аналітику" фейковими діями і плутається з реальною роботою сисадміна.
Реальний фронт цей заголовок ніколи не надсилає.

Приклад:
```bash
curl -X PATCH -H "x-pin: $PIN" -H "x-claude-verify: 1" \
  -H "Content-Type: application/json" -d '{"status":"working"}' \
  "$API/equipment/123"
```

Це стосується лише `equipment_log`. Для інших таблиць (daily_tasks,
assigned_tasks, assets, credentials, projects) при тестуванні — як і
раніше, створюй одноразовий запис із чітким префіксом (`TEST ...`),
перевіряй на ньому, видаляй одразу після. Ніколи не змінюй статус/поля
вже існуючих реальних записів "туди-сюди" для перевірки — навіть якщо
повертаєш значення назад, побічні ефекти (created_at змінних логів
тощо) можуть лишитись.

## Важливо при змінах
- Зміни в `schema.sql` НЕ застосовуються автоматично.
- Не хардкодити PIN або DATABASE_URL — тільки `process.env`.
- `ikorka-coo`/`ikorka-coo-backend` — окрема інфраструктура, не чіпати
  звідси.
